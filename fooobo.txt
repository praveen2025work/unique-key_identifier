# FOBO Reconciliation — Future-State Architecture

## 1. Objective

The objective is to establish an intelligent, agent-driven reconciliation process for Front Office (FO) and Back Office (BO) books, where reconciliation analysis is performed proactively before the controller arrives at the desk.

The solution will organize books into reconciliation groups at different business levels, with **Business Area Level 4 (L4)** representing a key reconciliation boundary. Each L4 contains a defined set of **Master Books** and has an assigned reconciliation owner/controller.

The future-state architecture introduces **Helix Agents and Agent 1** to continuously monitor book readiness, initiate reconciliation sessions, gather the required context and data, analyze breaks, and prepare an actionable reconciliation outcome for the controller.

---

## 2. Reconciliation Hierarchy

The logical reconciliation structure is:

**Business Area → L4 → Reconciliation → Master Books → FO / BO Books**

* **Business Area L4** is the reconciliation ownership boundary.
* Each L4 has one or more assigned controllers/users.
* Each L4 contains a defined set of Master Books.
* Each Master Book may represent Front Office, Back Office, or related book populations.
* A reconciliation session is created for the L4 once all required Master Books are ready.

---

## 3. Current-State Process

Today, the process is primarily controller-driven:

1. Master Books become ready in the underlying systems.
2. The controller determines whether the L4 is ready for reconciliation.
3. The controller opens the reconciliation process.
4. FO and BO data is reviewed.
5. Breaks are identified and investigated.
6. Additional information may be obtained from downstream/upstream systems.
7. The controller determines whether breaks:

   * Can be ignored / explained
   * Require further investigation
   * Require remediation or rectification
8. The controller completes the reconciliation and performs posting/actions where required.

The key limitation is that significant analysis happens **after the controller arrives at the desk**.

---

# 4. Future-State Process — Helix-Driven Reconciliation

In the future state, reconciliation becomes **proactive and agent-driven**.

### Step 1 — Book Readiness

The **One Finance UI / platform** publishes readiness notifications for Master Books.

The notification contains the relevant book and business context required to determine whether the associated L4 reconciliation can begin.

### Step 2 — Helix Agent Receives Events

The **Helix Agent** receives these notifications and evaluates the readiness of the Master Books associated with each L4.

The agent determines:

**Are all required Master Books ready for this L4 reconciliation?**

* **No →** Continue monitoring and wait for remaining books.
* **Yes →** Initiate the reconciliation session.

### Step 3 — Create Agent 1 Session

Once the L4 is ready, Helix creates an **Agent 1 reconciliation session** for that specific L4.

The session becomes the persistent execution context for the reconciliation.

The session is provided with:

* L4 context
* Master Book context
* Reconciliation configuration
* Applicable skills
* Supporting files/documents
* Business rules
* Required MCP tools
* Data-access instructions
* Relevant historical/evidence context

### Step 4 — Skill and Tool Execution

The configured skills determine which MCP tools and systems Agent 1 needs to access.

For example:

**Skill → MCP Tool → Source System → Data → Agent 1**

Agent 1 can retrieve the required information from FO, BO, reconciliation, reference, and other supporting systems.

The goal is to avoid requiring the controller to manually gather information across multiple systems.

---

# 5. Agent 1 Reconciliation Analysis

Agent 1 performs the reconciliation analysis across the relevant Master Books.

The analysis includes:

### Front Office vs Back Office

* Identify FO/BO differences
* Identify reconciliation breaks
* Group related breaks
* Determine break characteristics
* Identify known/expected differences
* Identify potential data-quality issues

### Break Investigation

Where additional information is required, Agent 1 can retrieve data from other systems through the configured MCP tools.

The agent can then determine whether a break appears to be:

**Explained / Ignore → Investigate → Rectify / Action Required**

The objective is not simply to identify a break, but to produce a **reconciliation-ready analysis** with supporting evidence.

---

# 6. Controller Experience

By the time the controller arrives at the desk, the L4 reconciliation should already have an analysis prepared.

The controller opens the L4 reconciliation and sees:

* Overall reconciliation status
* Master Book readiness
* FO vs BO position
* Break summary
* Break classification
* Agent analysis
* Supporting evidence
* Data retrieved from source systems
* Recommended actions
* Exceptions requiring human judgment

The controller can then interact with **Agent 1 using the same L4 session context**.

This allows the controller to ask follow-up questions without restarting the analysis.

For example:

> "Why is this break still outstanding?"

> "Show me the supporting evidence."

> "Check the corresponding transaction in the source system."

> "Can this break be explained by the timing difference?"

> "What needs to be rectified?"

The agent maintains the existing L4/Master Book context throughout the interaction.

---

# 7. Human-in-the-Loop Decision

The architecture should maintain a clear distinction between:

**Agent Analysis → Controller Decision → System Action**

The agent can perform analysis, gather evidence, identify patterns and prepare recommendations.

The controller remains responsible for the final business decision where human approval is required.

Where applicable, the controller can:

* Accept analysis
* Ignore/explain a break
* Request additional analysis
* Request additional data
* Initiate remediation
* Approve posting
* Reject the analysis
* Escalate the issue

---

# 8. Posting / Remediation

Once the controller confirms the required action, the reconciliation workflow can initiate the appropriate downstream action.

Examples include:

**Break → Investigation → Controller Approval → Rectification → Posting**

The architecture should clearly show that **analysis and execution are separate stages**, with appropriate controls between them.

---

# 9. Observability — Phoenix

**Phoenix** provides observability across the agent execution lifecycle.

It should capture:

* Agent sessions
* Agent reasoning/execution traces
* Skill execution
* MCP tool calls
* Tool inputs/outputs
* Errors
* Failed tool calls
* Missing context
* Agent failures
* Latency
* Repeated manual interventions
* Skill gaps

This creates a feedback loop:

**Agent Execution → Phoenix → Identify Skill Gaps → Improve Skills → Better Reconciliation**

The objective is to continuously identify where the agent cannot complete a reconciliation efficiently and determine whether the issue is caused by:

* Missing skill
* Missing MCP tool
* Missing data
* Poor data quality
* Incomplete business rules
* Incorrect context
* System availability
* Human decision requirement

---

# 10. Evidence & Audit

A dedicated **Evidence / Audit layer** should exist across the entire reconciliation lifecycle.

Every material decision should be traceable back to its source.

The audit trail should capture:

* L4
* Reconciliation/session ID
* Master Books
* Controller
* Agent session
* Skills used
* MCP tools invoked
* Source systems queried
* Data/evidence retrieved
* Breaks identified
* Agent analysis
* Controller interaction
* Controller decision
* Actions taken
* Posting/rectification
* Timestamp
* Final reconciliation outcome

This provides an end-to-end chain:

**Source Data → Agent Analysis → Evidence → Human Decision → Action → Final Outcome**

---

# 12. Executive-Level Message

The key message of the architecture should be:

> **"Move reconciliation from a controller-driven, reactive process to a proactive, agent-driven process where analysis is completed before the controller arrives at the desk."**

The architecture demonstrates three major changes:

### Today

**Controller → Gather Data → Investigate → Analyze → Decide → Act**

### Future

**Events → Helix → Agent 1 → Analyze → Evidence Ready → Controller Review → Decide → Act**

### Strategic Outcome

**Proactive reconciliation + intelligent analysis + human oversight + full evidence/auditability + continuous agent improvement**
